# 로컬 Git 기준점과 검증된 작업 단위 커밋

검증된 작업 단위의 변경 이력을 로컬에 남긴다. 사용자의 요청과 프로젝트의 Git 정책을 따르며, 로컬 커밋과 원격 반영·배포의 승인 범위를 구분한다.

## 원격 연결 없이 로컬 커밋한다

작업 환경은 GitHub 등 원격 저장소에 연결돼 있지 않아도 로컬 커밋이 가능하다. **원격 연결 없음과 로컬 Git 저장소 없음은 서로 다른 상태**다. `origin`·upstream·GitHub 로그인·네트워크 연결은 로컬 커밋의 전제 조건이 아니다.

- 로컬 저장소가 있으면 원격 유무와 무관하게 기존 저장소를 사용한다. remote가 비어 있다는 이유로 커밋을 생략하거나 저장소를 재초기화하지 않는다.
- 로컬 저장소도 없으면 아래 절차에 따라 작업 폴더에서 `git init` 후 기준점 커밋을 만든다. Git 저장소를 만들기 위해 GitHub 저장소 생성·로그인·`git remote add`를 요구하지 않는다.
- 초기화 직후에는 아직 커밋이 없어 `HEAD`·`git log` 조회가 실패할 수 있다. 이를 원격 연결 문제나 커밋 불가로 해석하지 않는다. 현재 상태와 staged 내용을 확인하고 첫 커밋을 만든다.

작업 변경은 **검증 → 사람 확인·커밋 승인 → 정확한 파일만 stage → 로컬 commit → 실제 SHA 확인**으로 기록한다. 공개 Skill을 내려받는 KIT 저장소와 작업 이력을 남기는 TASK 저장소를 구분한다. KIT에 원격이 있더라도 TASK에 복사·연결하지 않는다.

## 착수와 기준점

1. 현재 TASK에서 읽기 전용으로 저장소 유무·실제 저장소 루트·상태·최근 커밋을 확인한다. 상위 저장소에 속해 있으면 작업 범위와 일치하는지 확인하고 다른 프로젝트 변경을 읽거나 포함하지 않는다.
2. 로컬 Git 저장소가 없으면 반드시 알린다. 구현을 시작하기 전에 작업 폴더에 로컬 저장소를 초기화하고 기준점을 남기는 계획, 포함할 정확한 파일 목록을 제시한다. 초기화·기준점 커밋에 대한 사용자 승인을 받은 뒤 수행한다. 이미 해당 범위의 승인이 있으면 반복해서 받지 않는다. 분석 단계에서는 수행하지 않는다.
3. 이미 개발이 진행됐다면 지금 상태를 현재 시점의 기준점으로 기록한다. 과거 단계별 커밋이나 개발 전 상태를 재현한 것처럼 꾸미지 않는다. 사용자가 Git을 원하지 않거나 환경이 막으면 미사용 사유를 기록하고 승인된 작업 작업은 이어간다.
4. 로컬 커밋을 위해 원격 연결·전역 설정·다른 저장소를 바꾸지 않는다. 작성자 설정이 없어 실패하면 GitHub 인증 문제와 구분한다. 기존에 유효한 작성자 설정은 유지하고, 없으면 사용자에게 이름·이메일을 받아 해당 저장소의 `git config --local user.name`·`user.email`에만 적용한다. 개인 계정 로그인이나 토큰을 요구하지 않으며 신원을 지어내지 않는다.

## 의미 있는 작업 단위를 마칠 때

각 파일 저장마다 커밋하지 않고, 끝에 한 번에 몰아서 커밋하지도 않는다. 합의한 기능·업무 기준 변경·원인 수정 단위가 끝나면 아래를 제시한다.

- 변경 목적과 실제 변경 파일, 유지한 제약.
- 실행한 검사와 결과, 사용자 화면 확인 결과 또는 아직 미확인인 부분.
- 스테이징할 정확한 경로 목록과 제외할 파일.
- 아래 형식의 커밋 메시지 제안과 남은 한계.

사용자의 커밋 승인을 받은 뒤 그 목록만 스테이징한다. 승인은 짧은 응답("ㅇ")으로 충분하다. 승인된 목록·내용이 달라지면 변경을 먼저 알리고 승인을 갱신한다. 웹 동작의 완료를 주장하는 커밋은 사용자의 브라우저 확인을 받는다. 사용자가 미검증 상태를 보존하기로 명시적으로 결정했다면 그 한계를 드러내는 체크포인트로 남길 수 있으며 기능 완료로 보고하지 않는다.

## 커밋 메시지 — Conventional Commits, 한국어, 항목형

제3자가 `git log`만 읽어도 **무엇을 바꿨는지·왜 바꿨는지·어떻게 확인했는지** 알 수 있게 쓴다. 제목 한 줄로 끝내지 않는다. 본문은 서술 문단이 아니라 짧은 항목으로 쓴다.

```
fix(aggregate): 기간 집계에서 종료일 하루가 누락되던 문제 수정

변경:
- 종료일을 포함 경계(<=)로 비교하도록 집계 조건 수정
- 경계 날짜 표본 테스트 추가

이유:
- 미포함 경계로 처리해 마지막 날 주문이 합계에서 빠짐

확인:
- PASS: 마지막 날 주문 3건이 든 표본으로 합계 재계산 일치 (pytest tests/test_aggregate.py)
- UNVERIFIED: 타임존이 다른 입력의 날짜 경계

관련: R2, D3
```

- **제목**: `type(scope): 요약`. type과 scope는 Conventional Commits 관례대로 영문(`feat`·`fix`·`refactor`·`test`·`docs`·`chore`), 요약은 한국어로 50자 안팎. 결정·범위 변경은 `docs(decisions): …`. `git log --oneline`만으로 작업 흐름이 읽혀야 한다.
- **변경**: 동작·규칙·구조가 어떻게 달라졌는지 항목별로. 파일 이름만 나열하거나 diff를 옮겨 적지 않는다.
- **이유**: 어떤 요구·실패·담당자 답 때문에 바꿨는지.
- **확인**: 실제로 실행한 검사와 결과를 PASS/FAIL/UNVERIFIED로. 실행하지 않은 확인은 PASS로 쓰지 않는다. 가능하면 실행한 명령을 괄호에 남긴다.
- **관련**: DECISIONS·NOTES에 요구·결정·검증 ID가 있으면 적는다. 문서와 같은 표현을 쓴다.
- 항목 하나는 한 줄. 본문은 보통 10줄 안팎이며 장문 서술·배경 설명·코드 설명은 쓰지 않는다. 항목이 많아지면 커밋을 나눈다.

## 스테이징과 커밋 확인

- git add . / git add -A로 범위 전체를 무차별 포함하지 않는다. 원본 데이터·비밀값·KIT·임시파일·관련 없는 변경은 목적과 승인 없이 포함하지 않는다. 비밀값 자체를 채팅에 출력하지 않는다.
- 기존 staged 변경이 있으면 먼저 확인한다. 타인의 변경을 임의 unstage/reset하거나 새 커밋에 섞지 않는다. 분리할 수 없으면 해당 커밋을 보류하고 사용자에게 구체적으로 알린다.
- 커밋 직전 staged diff와 목록을 확인해 승인 범위·검사한 내용과 일치하는지 대조한다. 훅을 우회하거나 실패를 숨기지 않는다.
- 성공 후 실제 SHA·메시지·포함 파일·남은 변경을 확인하고 보고한다. 명령을 실행했다는 이유만으로 커밋 성공이라 하지 않는다.
- 로컬 커밋 승인이 Push·원격 백업·배포 승인까지 포함한다고 해석하지 않는다. 원격 작업을 요청받았다면 대상·전송 범위와 환경의 권한을 확인하고 해당 요청에 따라 수행한다.

기존 세션이 이전 스킬을 읽었다면 갱신된 이 지침을 다시 읽어야 한다. 파일이 바뀌었다고 실행 중인 Codex의 맥락이 자동 갱신됐다고 주장하지 않는다.
