# 검증은 예상과 실제를 비교해 다음 판단을 내리는 것

## 요구에서 검사를 만든다

각 필수 요구를 다음으로 연결한다.

> 요구/근거 → 구현 파일·함수 → 입력과 예상 결과 → 실행 명령·실제 결과 → 판정 → 한계/다음 조치

예상값은 작업 규칙·담당자 답·독립 계산·작은 수작업 사례에서 구한다. 구현 함수를 그대로 다시 호출해 같은 값을 만드는 것만으로 정답을 입증하지 않는다. 작업 원문·원본 데이터·기존 검사·기대값을 통과 목적으로 고치지 않는다.

상태:
- **PASS:** 해당 조건을 실제 실행/검산해 예상과 일치함.
- **FAIL:** 해당 조건에서 기대와 다르거나 검사 실행이 실패함. 환경 실패와 기능 실패를 구별.
- **UNVERIFIED:** 실행하지 못함/skip/설명만 있음/사람의 확인 대기.
- **STALE:** 관련 코드·입력·설정·정책이 바뀌어 이전 결과를 현재 근거로 쓸 수 없음.

파일 존재/문법·타입 검사, 서버 응답, 업무 기능의 정확성, 사용자 화면 확인은 서로 다른 증거다. 테스트 10개 통과를 “전체 기능 100%”라고 바꾸지 않는다. 파일 해시나 AI의 PASS 보고도 독립적인 기능 증명은 아니다.

## 검증한 코드와 실행 조건을 식별한다

중요한 검증에는 다음 중 결과 재현과 유효성 판단에 필요한 정보를 기존 기록·로그와 연결한다. 같은 실행 조건을 여러 행에 복사하지 말고 공통 기록을 참조해도 된다.

- **코드 상태:** 로컬 Git이 있으면 실제 커밋 SHA와 검사 대상의 미커밋 변경·새 파일 여부를 함께 남긴다. SHA만으로 수정 중인 코드를 식별하지 않는다. Git이 없거나 정확한 상태 구분이 필요하면 관련 파일의 해시·보존된 diff 등으로 검사한 상태를 식별한다. 이를 위해 새 저장소나 별도 검증 시스템을 의무화하지 않는다.
- **입력·설정:** 사용한 입력/fixture·정책의 경로 또는 버전, 결과를 바꾸는 설정을 기록한다. 실행 후 값이 바뀔 수 있는 입력을 경로만으로 구별하기 어렵다면 해당 버전이나 해시를 남긴다. 비밀값은 기록하지 않는다.
- **검증 종류·연결 방식:** 단위·정적 검사·로컬 통합·모의 연동·실제 외부 연동·화면 확인 중 실제 수행한 범위와 실행한 모드를 구분한다. 실제 연동은 허용된 호출 경로와 민감값을 제외한 응답 등 관찰 근거가 있어야 하며, 종류 이름만 붙여 입증하지 않는다.
- **실행 근거:** 명령/동작, 종료 상태와 핵심 관찰값, 확인 주체, 보존한 로그가 있으면 실제 위치를 연결한다. 파일을 만들지 않았다면 로그 경로를 지어내지 않는다.

검증 중 관련 코드·입력·설정이 바뀌었거나 검사한 상태를 특정할 수 없다면 현재 상태의 PASS로 재사용하지 않는다. 관련 근거를 STALE 또는 UNVERIFIED로 표시하고 필요한 검사만 다시 한다. 같은 상태의 유효한 결과는 재사용한다.

## 설계 문서도 실제 코드와 대조한다

중요 결정 D…에는 관련 요구 R…와 검사 E…를 연결한다. README/허용된 설계 문서가 주장하는 필드·타입·검증 위치·교체 파일·환경 변수 이름이 실제 구현과 일치하는지 확인한다. 스키마 파일의 존재나 타입 검사만으로 필드 요구 충족을 판정하지 않는다. 실제/모의 교체를 설명했다면 각 구현의 존재와 선택 경로, 실제로 실행해 본 모드를 구분한다. 외부 연결을 검증하지 못하면 해당 모드는 UNVERIFIED다.

구현 PASS, 문서화 완료, 사용자 설명 확인은 별개다. 문서가 빠지면 문서화 미완료로 기록하고, 함수 검사가 통과해도 사용자가 이유·대안을 설명하지 않았다면 이해는 미확인이다. 반대로 설명을 잘했더라도 기능 검증이 미실행이면 PASS가 아니다.

코드·정책·설정이 바뀌면 관련 검사와 문서가 오래됐는지 확인한다. 선택 이유나 성립 조건이 달라진 결정은 이해 확인도 갱신한다. 전체 기록을 매번 초기화하지 않는다.

## 중요한 검사가 오류를 잡는지 확인한다

피해가 큰 계산·판정·경계 규칙은 독립적인 기대값과 반례로 검사한다. 실제 결함이 있으면 수정 전에 실패를 재현하고 같은 검사·입력·기대값으로 수정 후 통과를 확인하는 근거를 우선한다. 검사나 기준을 정당하게 바꿨다면 새 기준에서 다시 확인하고 동일 조건의 실패→통과라고 기록하지 않는다.

오류 검출력이 여전히 불명확하고 확인 비용이 타당한 경우에만 격리된 복사본에서 규칙 하나를 의도적으로 틀리게 바꿔 해당 검사가 실패하는지 확인한다. 예: 종료일 포함 조건을 `<=`에서 `<`로 바꿨을 때 경계 사례가 실패하는가. 실행 명령이 복사본을 대상으로 하는지 확인하고 원본·기존 검사·기대값은 보존한다. 변경한 복사본으로 실제 외부 부작용을 실행하지 않는다.

의도한 동작 차이를 잡아서 실패했는지 확인한다. 문법 오류·실행 환경 오류는 규칙의 오류를 잡았다는 근거가 아니다. 잘못된 규칙인데도 통과한다면 그 상태에서 검증했다고 주장하지 말고 빠진 사례나 잘못된 검사 대상을 조사한다. 이때 주입한 오류는 검사 점검용임을 밝히며 실제 제품 결함을 발견한 것처럼 기록하지 않는다.

모든 검사에 변형 검증이나 테스트 우선 작성을 강제하지 않는다. 실제 실패→수정→통과로 충분한 근거가 있으면 추가 실험을 생략한다. 이 선택 검사를 생략했다는 이유만으로 충분히 검증된 필수 요구를 미검증으로 돌리지 않는다.

## 검증 수준

1. 변경 직후에는 바뀐 요구와 실제 실패 사례를 우선 검사한다.
2. 주요 작업 완료 때는 그 작업의 필수 동작·경계·주변 정상 동작을 확인한다.
3. 인계 전에는 최종 코드/입력/설정으로 전체 필수 요구와 실행·전달 형식을 확인한다. 같은 코드의 동일 검사를 이유 없이 반복하지 않는다.

작업에 맞는 반례를 선택한다.
- 데이터: 빈 입력/누락/중복/잘못된 값/날짜·단위·분모/제외 규칙/반올림. 결측을 임의 0으로 만들거나 제외하지 않는다.
- 검색·정책: 답 없음, 잘못된 출처가 유사어로 검색됨, 문서 충돌, 적용 기간 차이. 인용이 있다는 것과 답이 맞다는 것을 따로 검사.
- 웹·상태: 입력 오류, 빈 결과, 로딩·갱신 실패, 이전 데이터 표시, 재시도·새로고침·저장 복구.
- 규칙: 경계와 예외 우선순위, 규칙 없음, 중복 실행의 영향.
- 예측: 누수·시간 분할·기준선·실패 비용에 맞는 지표. 해당 작업일 때만.

## 결과에 따른 다음 행동

- 예상과 일치: 검사한 요구를 완료로 기록하고 다음 필수 단위로 진행.
- 예상과 다름: 원인·수정 범위부터 설명하고 최소 수정 후 같은 사례 재검증.
- 요구 자체가 바뀜: 결정 문서와 구현·검사 모두 갱신. 예전 PASS는 관련 범위에서 STALE.
- 증거 없음: 미검증으로 두고 실제 확인 방법을 제시. 필수 요구의 미검증은 결과물 전달 위험으로 알림.

명령·중요 출력·입력/설정·확인 주체(AI 실행/사용자 직접)를 필요한 만큼만 기록한다. 보안값과 불필요한 원본 전체를 복사하지 않는다. 타이밍·승인·실행 결과를 사후에 만들지 않는다.

웹은 실제 환경에서 허용된 함수·HTTP·CLI·브라우저 도구로 검사한다. 자동 검사의 통과 범위와 사람이 직접 확인한 범위를 구분한다. 사람의 확인이 필요한 사용성·업무 적합성은 실제 답을 받기 전까지 UNVERIFIED다.
