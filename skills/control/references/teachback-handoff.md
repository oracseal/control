# 기술 의도 이해와 인계 품질

중요한 설계 선택을 설명하거나 작업 결과를 인계할 때 적용한다. 현재 구현·자료·검증 근거를 바탕으로 사용자가 판단을 이어갈 수 있도록 돕는다.

## 중요한 선택 뒤 짧게 이해 확인

실제 코드·자료를 바탕으로 목적, 입력→처리→출력, 선택 이유와 대안, 실패 조건, 실제 검증을 설명한다. 사용자가 핵심 하나를 자기 말로 말해 보게 한다. 모든 수정마다 퀴즈를 내거나 전 코드를 암기시키지 않는다.

사용자가 정한 업무 목표에 대한 설명과 **AI가 고른 기술·처리 방식에 대한 이해**를 별도로 확인한다. [AI 선택과 이해 확인](ai-decisions.md)의 D…별 결정 주체·선택 근거·버린 대안·성립 조건·위험·재검토 조건을 사용한다. 코드의 동작을 설명하는 것만으로 AI의 선택 이유까지 이해했다고 판정하지 않는다.

예:
- 이 입력은 어느 함수에서 어떤 규칙으로 결과가 되는가?
- 이 규칙이 바뀌면 어느 파일과 검사를 바꿔야 하는가?
- 더 단순한 대안 대신 이 구조를 고른 이유는 무엇인가?
- 테스트 통과와 아직 확인하지 못한 사용자 행동은 각각 무엇인가?
- 사용한 Skill/도구가 실제로 해결한 작업과 한계는 무엇인가?
- AI가 이 라이브러리/자료구조를 고른 이유와 채택하지 않은 대안은 무엇인가?
- AI가 둔 임계값이나 예외 처리는 어떤 근거·가정에 의존하며, 그 조건이 틀리면 어떤 결과가 나오는가?

“다 이해했지?”나 정리된 설명을 읽어 주는 것으로 확인을 대신하지 않는다. D…별 **미확인/재설명 필요/설명 확인**을 구분한다. 이유·대안·성립 조건에 대한 실제 답을 확인하고, 중요한 오해를 교정했다면 다시 말한 답으로 확인한다. 답변이 없으면 미확인으로 두고 독립적인 승인 작업은 이어간다. 막힌 부분은 인계 전에 코드·자료를 보며 교정한다. AI가 한 검증을 사용자가 직접 한 것처럼 기록하지 않는다.

## 결과물의 완성도

최종 결과를 아래 관점으로 실제 확인한다. 작업에 없는 형식을 강제하지 않는다.

- **제품:** 필수 사용자 흐름이 끝까지 동작하는가? 입력·빈 결과·실패/복구 상태가 이해 가능한가?
- **구조:** 책임 분리·데이터 계약·업무 규칙 위치·실제/모의 연결 경계가 설명 가능한가? 복잡도가 작업 규모에 맞는가?
- **정확성:** 필수 요구의 예상과 실제를 비교했는가? 중요한 반례·회귀가 남아 있지 않은가?
- **실행/인계:** 필요한 런타임·명령·포트·경로·데이터와 수정 지점이 명확한가?
- **일치:** 구현, 결정 기록, 검증 결과, 주장하는 성과가 일치하는가? 업무 성과를 측정하지 않았는데 달성했다고 하지 않는가?
- **설계 문서:** README 또는 허용된 설계 문서에 실제 스키마·설계 이유·교체 지점·환경 변수/설정·전환 검사·한계가 적혀 있고 코드와 일치하는가? 없는 구조·연결을 문서로 만들어내지 않았는가?

파일·타입·테스트·Skill의 개수를 품질로 대신하지 않는다. 자동 검사 결과와 사람의 사용 확인은 구분하며, 사용자 확인이 필요한 사용성·업무 적합성은 실제 답을 받기 전까지 UNVERIFIED로 남긴다.

## 인계와 최종 확인

사용자가 문제/범위, 핵심 흐름, 결정과 대안, 실제 검사 한 사례, 실패 조건, 실행/수정 방법을 자기 말로 설명할 수 있도록 돕는다. 필요한 경우 코드와 문서를 함께 보며 확인한다. 인계 직전에 처음 배우지 않도록 작업 중에도 나누어 설명한다.

이때 중요한 **AI 결정 중 미확인/재설명 필요**인 항목을 우선한다. AI가 설명한 문장을 그대로 반복하게 하지 말고 “조건이 달라지면 왜 다른 선택이 필요한가”까지 확인한다. 근거가 임시 가정인 항목은 그 불확실성도 설명할 수 있어야 한다. 선택 이유가 바뀐 경우 이전의 설명 확인을 그대로 재사용하지 않는다.

최종 코드/입력/설정 기준으로 필수 산출물·경로·저장 상태·커밋되지 않은 변경·실행·최근 검사·FAIL/UNVERIFIED·남은 한계를 확인한다. 전달 요구가 있는 문서는 지정 형식으로 작성한다. 필수 원문·데이터·기존 검사를 덮어쓰지 않는다.

주요 설계는 구현 위치·문서 절·검사 근거를 함께 확인한다. README가 수정 금지면 원문을 보존하고 허용된 별도 설계 문서에 작성한다. 문서·기능·이해 중 부족한 항목을 따로 보고하며 이해 상태만으로 결과물 전달을 막지 않는다. 관련 없는 문서 양식이나 불필요한 계층을 추가하지 않는다.

에디터 저장 충돌과 실제 전달 대상을 확인한다. KIT·임시파일·상태 기록의 혼입을 살피되 임의 삭제하지 않는다. .gitignore만으로 패키징 도구의 제외 동작을 보장하지 않는다. 원격 전송·공개·배포는 사용자가 요청한 범위와 프로젝트 절차에 따라 수행하며 실제 완료 여부를 확인한다.

## 결과물 전체의 준비 상태를 판정한다

개별 검사의 PASS/FAIL/UNVERIFIED/STALE와 별도로, 최종 결과물이 합의한 전달 조건을 갖췄는지 다음 중 하나로 보고한다.

| 판정 | 기준 |
|---|---|
| **준비됨** | 필수 동작·산출물·필수 문서·저장 상태와 필요한 검증이 현재 결과물에서 확인됐고, 전달을 막는 알려진 문제가 없음. |
| **수정 필요** | 필수 요구 실패, 필수 파일 누락, 미해결 저장 충돌 등 확인된 문제가 있음. |
| **확인 불가** | 확인된 필수 실패는 없지만, 접근 제한·미실행·오래된 근거 등으로 필수 항목을 판단할 수 없음. |

알려진 필수 실패와 미검증이 함께 있으면 **수정 필요**로 판정하고 미검증 항목도 함께 알린다. 관련 없는 선택 검사의 미실행이나 사용자 이해 미확인만으로 충분히 검증된 결과물의 전달을 막지 않는다. 필수로 합의한 사용자 동작 확인이 남아 있다면 그 항목은 확인 불가의 근거가 된다. 선택·필수 구분을 바꿔 실패를 숨기지 않는다.

최종 보고에는 판정과 이유, 남은 필수 조치·미검증·한계, 결과물 위치와 실행 방법, 사용자의 다음 행동을 짧게 담는다. 이해 상태는 별도로 알린다. **준비됨은 실제 전달·공개·배포 완료나 그 행동의 승인을 뜻하지 않는다.** 실제 수행 여부는 해당 작업의 결과로 따로 확인한다.
