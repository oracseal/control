# 문제 이해, 제품과 구조, 적은 비용으로 결과 만들기

## 요청 기능과 실제 문제를 구분한다

“대시보드/챗봇을 만들어라”는 산출물 요구다. 그것이 필요한 사용자 행동, 현재 병목, 실패 비용을 자료로 확인한다. 요청 기능은 지키면서 원인 가설을 검증한다. 분석만 오래 하다가 필수 결과물을 놓치지 않는다.

- 현상: 자료에 실제로 있는 값·관찰·불편.
- 원인 가설: 왜 그런 현상이 생긴다고 생각하는가, 이를 지지/반박하는 증거는 무엇인가.
- 해결 가설: 어떤 변경이 어떤 사용자 행동을 개선하는가.
- 검증 범위: 기능이 동작하는 것과 운영 성과가 개선된 것은 다르다. 운영 측정이 없으면 효과를 보장하지 않는다.

첫 자료 점검은 결론을 바꿀 부분에 집중한다. 모든 파일을 무작정 출력하지 않는다. 자료 충돌, 결측, 집계 범위, 날짜/단위, 데이터 출처, 승인 권위를 확인한다. 자료에 없는 숨은 조건을 창작하지 않는다.

## 작업 유형에 맞는 최소 접근

- **웹/도구:** 사용자 핵심 행동 1개를 입력→검증→처리→표시/저장까지 연결. 로딩·빈 상태·실패·재시도를 해당 위험에 맞게 설계.
- **데이터 분석:** 분모·포함/제외·기간·단위·결측 처리부터 정의. 독립 계산이나 작은 수작업 예제로 주요 결론 검산.
- **검색/문서 답변:** 검색된 문장이 질문에 답하는지, 정책 충돌·적용 시점·답 없음 처리를 확인. 출처 개수만 늘리지 않는다.
- **규칙/자동화:** 우선순위·경계 포함·예외·재실행/중복·실패 뒤 상태를 확인. 규칙 없는 상태를 정상 판정으로 처리하지 않는다.
- **예측:** 요구가 있을 때만 모델을 선택. 단순 기준선, 분할/시간 순서, 누수, 잘못된 판단의 비용에 맞는 지표 확인.

모든 작업에 웹·DB·모델·서버를 강제하지 않는다.

## 사용자가 결과의 상태를 구별할 수 있게 한다

실제 작업에서 가능한 정상 완료·부분 처리·대체 동작·실패를 구분하고, 각 상태에서 결과를 어디까지 믿고 사용할 수 있는지 정한다. 내부 로그뿐 아니라 화면·CLI 출력·보고서 등 사용자가 받는 결과에도 드러낸다.

- 일부만 처리했다면 성공한 범위와 누락·실패 범위를 알린다. 건수를 알 때만 수치를 쓰며, 전체 처리가 필수라면 부분 결과를 전체 완료로 판정하지 않는다.
- 외부 연결 실패 뒤 예제·모의·캐시 결과를 제공한다면 대체 여부와 한계, 확인 가능한 데이터 시점을 표시한다. 실패를 빈 결과나 정상 성공으로 바꾸지 않는다. 대체 기능이 동작해도 원래 요구를 충족했는지는 따로 판정한다.
- 실패 시 결과가 저장됐는지, 이전 결과가 남는지, 재시도·입력 수정 등 어떤 다음 행동이 가능한지 설명한다. 원인을 확인하지 못했으면 추측을 확정 안내로 쓰지 않는다.

요구에 없는 대체 기능을 추가할 필요는 없다. 중요한 상태는 실제로 재현해 결과와 안내가 일치하는지 확인하고, 웹의 구체적인 확인은 [실패 상태 검증](web-runtime.md)을 따른다.

## 구조 설계와 대안 비교

현재 구조를 읽고 실제 책임으로 나눈다. 예: 입력 읽기/업무 규칙/결과 표현. 작은 작업라면 함수 분리로 충분할 수 있다. 계층·파일·서비스를 늘리려면 해결하는 변경 위험을 설명한다.

선택할 구조는 다음을 답할 수 있어야 한다.
- 입력과 출력의 형식/필수 값, 어디에서 검증하는가?
- 업무 계산/정책의 책임은 어디인가? UI와 섞여 있으면 어떤 수정이 어려워지는가?
- 상태를 어디에 두며 새로고침·실패·재시작 시 어떻게 되는가?
- 외부 서비스와 모의 구현은 어떻게 구분되며 교체 지점은 어디인가?
- 주요 규칙 변경 시 어느 파일과 검사를 바꿔야 하는가?

실제 작업에 필요한 항목만 정의한다. 타입·스키마가 있더라도 실제 필드와 런타임 입력 검증이 맞는지 확인한다. “타입 파일이 있다”를 유지보수성 증거로 끝내지 않는다.

## 구현된 설계의 근거를 설계 문서에 남긴다

중요한 스키마·책임 분리·서비스 경계가 구현될 때 README의 설계 절을 함께 갱신한다. README가 수정 금지인 수정이 제한된 요구사항 원문이면 내용을 보존하고 허용된 설계 문서(예: docs/DESIGN.md)에 작성한다. 작업에서 지정한 설계 문서가 있으면 그 위치가 우선이다. 연결 가능한 편집 허용 문서에 링크하고, 원문을 수정할 권한은 링크를 넣기 위해서도 확대하지 않는다.

문서에는 구현한 항목만 구체적으로 남긴다.

| 항목 | 필요한 설명 | 대조할 실제 근거 |
|---|---|---|
| 구조와 책임 | 핵심 입력→처리→출력, 파일/함수별 역할, 분리한 이유와 대안 | 실제 호출 흐름과 결정 D… |
| 데이터 스키마 | 실제 필드·타입·필수/선택 여부·기본값·제약, 이 구조를 고른 이유 | 타입/스키마 파일, 런타임 검사 위치, 검증 E… |
| 실제/모의 경계 | 인터페이스, 각 구현 파일, 호출·선택 위치 | 실제 연결 코드와 실행한 모드 |
| 교체 방법 | 변경할 파일·설정·환경 변수 이름, 전환 절차, 전환 후 검사 명령과 기대 결과 | 현재 코드가 실제로 읽는 설정·변수, 관련 검사 |
| 한계 | 아직 없는 구현·연결·미검증 조건, 운영에 필요한 추가 작업 | FAIL/UNVERIFIED와 미완료 요구 |

환경 변수는 이름과 용도만 쓰고 실제 비밀값은 남기지 않는다. 변수가 없으면 "환경 변수 없음, 해당 파일/함수에서 선택"처럼 실제 구조를 설명한다. 모의 구현만 있으면 실제 서비스 연결은 미구현이라고 밝힌다. 문서를 채우기 위해 불필요한 어댑터·계층·환경 변수를 추가하지 않는다.

완료 조건은 **코드에 존재함 + 문서의 정확한 위치·설계 근거 + 관련 동작 검증**이다. 문서의 설명만으로 구현이나 검증을 대신하지 않는다. AI 선택의 이유·대안은 [AI 결정 설명](ai-decisions.md)에 따라 사용자 이해와도 연결한다.

대안은 보통 두 개면 충분하다. 사용자 가치/필수 요구 충족, 구현 시간, 의존성·운영 비용, 검증·이해 비용, 남는 위험으로 비교한다. 기존 스택/간단한 규칙/파일 저장으로 충분하면 새 프레임워크·DB·AI 호출을 추가하지 않는다. 필요하면 복잡도를 받아들이되 이유를 적는다.

## 첫 응답에서 전체 설계와 작업 계획을 연결한다

전체 설계는 주요 책임과 데이터 흐름, 입력 계약·상태·실패 처리·외부 연결 중 필요한 경계를 설명하는 초안이다. 구현을 시작하기 전에 첫 기능만이 아니라 필수 결과물을 끝까지 만드는 경로를 보여 준다. 모든 파일·함수·화면을 미리 확정하거나 추상 계층을 늘리지 않는다. 미확인 업무 기준에 의존하는 부분은 가정과 결정 필요 지점을 표시한다.

첫 응답에는 전체 설계와 전체 계획표가 실제로 보여야 한다. 설계는 핵심 입력에서 출력까지의 흐름과 각 책임, 중요한 데이터·상태·외부 연결 경계, 추천 대안과 미정인 부분을 짧게 설명한다. 기술 이름이나 첫 기능 이름만으로 전체 설계를 대신하지 않는다.

작업 규모에 맞춰 보통 3~6개 작업 단위로 아래 계획표를 제시한다. 행은 실제 요구에 맞게 채우며, 단순한 작업을 단계 수에 맞춰 부풀리지 않는다. 같은 정보가 담긴 프로젝트 지정 형식이 있으면 그 형식을 따른다.

| 단계 | 필수 요구·완성할 결과물 | 선행 조건·AI 작업 | 검사 입력/예상 결과·완료 조건 | 사용자/담당자 확인 내용·시점 |
|---|---|---|---|---|

모든 필수 요구가 어느 단계에서 구현·검증되는지 배치한다. 첫 작업의 파일·검사를 상세화하되 뒤 단계도 확인 가능한 결과와 검증을 적는다. "추후 기능 추가·전체 검증"만 적거나 전체 계획을 내부 생각으로 남긴 채 첫 작업만 보고하면 첫 분석은 불완전하다. 미확정 정책은 억지로 결정하지 않고 답에 따라 바뀔 단계와 독립적으로 진행할 단계를 표시한다.

첫 실행 경로 → 필수 요구 확장 → 중요한 실패·경계 확인 → 최종 검증·설계 문서·본인 설명·인계 확인이 이어지는지 본다. 이 순서를 모든 작업에 기계적으로 적용하지 않는다. 예를 들어 데이터의 의미가 불명확하면 집계 기준 확인이 먼저이고, 실행 환경이 불확실하면 최소 실행부터 확인한다. 설계 문서와 이해 확인은 구현 중에도 갱신한다.

- 각 필수 요구가 어느 작업과 검사에 연결되는지 빠짐없이 대조한다.
- 담당자 대화는 답변 범위 확인과 작은 질문에서 시작하고 실제 답에 따라 다음 질문을 발전시킨다. "담당자에게 문의" 대신 지금 보낼 질문과 뒤 단계에서 확인할 주제를 구별해 쓴다. 아직 받지 않은 답을 전제로 후속 질문을 확정하지 않는다. 업무 기준이 구체화되면 어떤 결정·검사가 달라지는지도 연결한다. 탐색 질문에 당장의 코드 변경을 요구하지 않으며, 답변/검증이 필요한 단계와 독립적으로 진행할 단계를 구별한다.
- 확인 시점은 "첫 실행 결과가 나온 직후", "업무 규칙을 확정하기 전", "자료의 집계가 어긋나면"처럼 단계나 관찰 조건에 붙인다. AI의 직접 검사, 사용자의 화면 확인, 담당자의 업무 기준 답변을 분리하고 필요한 동작·질문과 판단 근거를 제안한다.
- 시간 예산·마감이 주어졌다면 확인 시점에 예상 경과 시간이나 남은 시간 기준을 함께 제안할 수 있다. 이는 조정 가능한 계획값이며 실측 소요나 현재 시각처럼 단정하지 않는다. 시간 정보가 없으면 단계·조건 기준으로 계획하고 임의의 마감을 만들지 않는다. 최종 실행·문서·본인 설명·인계에 필요한 작업도 포함한다.
- 각 대화와 작업 단위 종료에 실제 상태·확인된 시간과 계획을 대조한다. 확인할 때가 됐으면 이유와 구체적인 질문/동작을 먼저 제안하고, 새 답·검증 결과·지연으로 순서와 시점을 바꾸면 관련 계획을 갱신한다. 예약 알림 기능이 없는 상태에서 특정 분에 자동으로 메시지를 보낸다고 약속하지 않는다.

첫 응답을 끝내기 전에 전체 설계, 모든 필수 요구의 단계와 검증, 사용자/담당자 확인 시점, 첫 실행 범위가 모두 드러나는지 확인한다. 그 뒤 사용자에게 필요한 결정만 요청한다. 전체 계획은 검증하며 바꾸는 초안이며 이후 대화를 처음 계획에 맞추기 위해 새 근거를 무시하지 않는다.

## 작업 분해와 중간 점검

각 작업은 “기능 이름”만이 아니라 다음을 포함한다.

> 작업 A: 사용자에게 보일 결과 / 관련 요구 / 선행 조건 / 읽을 자료 / 바꿀 파일 / 유지 조건 / 예상값이 있는 검사 / 사용자·담당자 확인 / 다음 판단

먼저 작은 실행 경로를 완성하고 이후 필수 요구를 빠짐없이 확장한다. 핵심 화면 실행이 막혔다면 장식·추가 통계보다 해결을 우선한다. 불확실한 조건 하나 때문에 독립적인 필수 작업 전체를 멈추지는 않는다.

작업 종료에는 결과·검증·남은 위험을 보여 주고 다음 작업을 추천한다. 사용자 확인·커밋 승인이 합의된 중단 지점이면 답을 기다린다. 승인 범위의 독립 작업까지 막거나 매 파일마다 승인을 요구하지 않는다.

방향을 바꿀 신호를 미리 정한다. 예: 원본 집계가 보고와 다름, 정책 문서가 상충함, 서버를 실행할 수 없음, 단순 방법이 필수 정확도를 만족하지 못함. 매 대화에서 이 신호와 현재 계획을 대조한다. 신호가 나타나면 이전 계획·새 근거·바꿀 단계·유지할 제약·다음 검사를 설명한다. [작업 기록](work-record.md)의 현재 계획을 갱신하고 바뀐 이유를 남긴다. 단순 순서 조정과 업무 기준·필수 범위를 바꾸는 결정을 구분한다.
