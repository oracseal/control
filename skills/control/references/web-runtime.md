# 실행되는 제품과 미리보기

웹 작업일 때만 사용한다. 기존 README·실행 스크립트·의존성을 읽고 최소 기능부터 실제로 실행한다. HTML 소스를 만들었다는 것과 사용자가 화면을 열었다는 것은 다르다.

## 확인 순서

1. 정확한 작업 폴더와 런타임/의존성, 실제 서버 명령을 확인한다.
2. 허용된 도구로 실행하고 서버 출력의 실제 포트와 준비 상태를 확인한다. 실행 중인 프로세스를 완료로 오해하지 않는다.
3. 실행 환경에 맞는 호스트·포트·경로를 확인한다. 로컬 확인은 기본적으로 루프백 주소를 사용하고, 컨테이너·원격 미리보기에서 요구하는 경우에만 0.0.0.0 등 필요한 바인딩을 선택한다. 외부 공개·터널 연결은 사용자의 요청과 환경 권한을 확인한다.
4. AI는 허용된 HTTP/함수·브라우저 검사를 하고, 사용자에게 실제 접속 주소와 핵심 사용 확인 2~3개를 제시한다. 각 확인에 동작과 예상 결과를 붙이며 자동 검사와 사람의 사용 확인을 구분한다.
5. 입력→결과, 필터/저장/갱신 등 필수 흐름과 중요한 실패 상태를 사람이 확인한다. 확인 결과를 들은 뒤에만 사람 확인 완료로 기록한다.

서버 터미널은 미리보기 동안 유지한다. 탭 종료/Ctrl+C로 서버가 끝날 수 있다. 오래된 화면·실패 시 상태·데이터 시점을 사용자가 구별할 수 있어야 한다.

## 실패·부분 처리·대체 결과의 화면 검증

현재 기능에 해당하는 중요한 실패 경로를 허용된 테스트 입력·응답으로 재현한다. 예: API 오류/시간 초과, 일부 항목 처리 실패, 갱신 실패 뒤 이전 결과 표시. 실제 서비스에 장애를 일으키지 않으며, 모의 오류 응답으로 확인한 범위와 실제 연동 검증을 구분한다.

- 전체 성공 문구와 수치가 부분 처리·실패를 감추지 않는가? 처리 범위와 빠진 항목을 사용자가 구별할 수 있는가?
- 모의·예제·이전 데이터가 최신 실제 결과처럼 보이지 않는가? 해당되는 경우 대체 표시와 확인된 데이터 시점이 있는가?
- 저장 상태와 가능한 다음 행동이 명확한가? 재시도가 저장·외부 작업을 중복시킬 수 있는 기능이면 그 영향도 확인했는가?

각 사례의 입력/응답 조건, 예상 상태·안내, 실제 관찰 결과를 기존 검증 기록에 연결한다. 로그의 오류만으로 화면 안내까지 확인했다고 하지 않는다. 허용된 브라우저 도구로 확인하거나 사용자에게 재현 동작과 예상 화면을 안내하고 실제 답을 받는다. 화면을 확인하지 못했다면 그 부분은 UNVERIFIED다.

## 막혔을 때

- 연결 거부: 프로세스 생존, 실제 포트·호스트, 허용된 연결 경로.
- 포트 충돌: 소유 프로세스 확인 후 본인 작업 서버인지 판단. 임의 프로세스 종료 금지.
- 404: 화면/API 요청 경로와 서버 라우트.
- 권한 차단: 코드 오류와 구별하고 실제 환경의 승인 절차나 지원 경로를 확인한다. 권한을 우회하거나 관련 없는 설정을 변경하지 않는다.
- 화면만 오래됨: 에디터 저장, 실제 실행 파일, 캐시·재조회, 서버 오류 순으로 확인.
- API 성공인데 UI 실패: 응답 스키마·브라우저 오류·DOM 갱신 등 근거를 조사. HTTP 200을 UI 완료로 취급하지 않는다.

서버가 막힌 채 장식/추가 기능을 계속 만들지 않는다. 원인·다음 시도를 좁히고 독립적인 필수 작업을 진행할 수 있는지 판단한다. 작업 앱 문제와 플랫폼 자체 장애를 구분한다.
