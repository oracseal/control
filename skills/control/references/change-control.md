# 실패 원인과 변경 범위부터 확인하기

## 수정 전 보고

버그 보고·테스트 실패·결과 불일치·요구 변경을 받으면 먼저 관련 자료와 현재 코드를 읽는다. “전체 리팩토링하면 해결”이라고 추측하지 않는다.

1. **재현:** 어떤 입력/동작에서 예상과 실제가 어떻게 다른가. 실제 명령·오류와 위치는 무엇인가.
2. **원인:** 관찰 근거로 확인한 원인인가, 아직 검증할 가설인가. 원인·증상·업무 요구 변경을 구분한다.
3. **수정 범위:** 바꿀 파일/함수와 필요한 이유. 영향받는 호출부·데이터·인터페이스.
4. **유지할 조건:** 기존 정상 사례, 원본 데이터, API/출력 형식, 업무 기준 등.
5. **검증 계획:** 기존 실패 재현, 수정 후 기대 결과, 영향을 받는 정상/경계 사례.

이 다섯 항목을 짧게 먼저 알린다. 사용자가 합의한 범위 안의 구현 오류면 이어서 수정한다. 업무 기준·허용 범위·외부 연결을 바꾸는 해결책이면 추천안과 영향을 제시하고 그 결정만 받는다.

## 원인 조사와 최소 변경

- 관찰→가설 하나→구별 가능한 검사→결과 순서로 좁힌다. 오류 문구만 보고 원인을 확정하지 않는다.
- 로직 오류, 입력 오류, 가정 오류, 실행 환경/권한 문제를 구분한다. 권한 오류를 앱 코드 전체 재작성으로 해결하려 하지 않는다.
- 같은 근거로 두 번 실패하면 같은 시도를 멈추고 다른 가설을 고른다. 사용자에게 실제 경과가 확인된 경우 약 5분 정체도 접근 변경 신호다. 시간은 추정하지 않는다.
- 최소 변경 뒤 같은 실패 입력을 다시 실행한다. 업무 결과에 영향을 받는 주변 사례도 검사한다.
- 원본·기존 테스트·기대값을 바꿔 통과시키지 않는다. 기대값 오류가 의심되면 근거를 제시하고 구현 오류와 분리한다.
- 원인을 확정하지 못해도 증상·미확인 가설·막힌 이유·가능한 다음 조치는 남긴다. 다른 독립적인 필수 작업은 계속할 수 있다.

## 방향 조정과 기록

새 증거로 접근이 바뀌면 이전 결정의 이유, 바뀐 증거, 새 결정, 영향받는 요구/설계/작업 순서/코드/검증, 남는 위험을 연결한다. 현재 계획의 어느 단계를 재검증·앞당김·보류할지 정하고 관련 기록을 갱신한다. 기존 기록을 조용히 고쳐 처음부터 알았던 것처럼 만들지 않는다. 현재 유효한 결정은 문서 상단에서 찾을 수 있게 한다.

최종 보고: 실패가 실제로 재현됐는가 → 원인이 무엇이었는가 → 무엇만 바꿨는가 → 같은 사례와 주변 검사가 어떻게 됐는가 → 아직 남은 위험은 무엇인가.
