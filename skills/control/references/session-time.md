# 세션 복구와 제한된 시간의 우선순위

## 중단 후 재개

1. 사용자에게 알려진 현재 단계와 TASK 경로, 마지막 요청을 확인한다. 작업이 중단된 상태면 재개 요청의 범위를 확인한다.
2. 기존 대화를 이용할 수 있으면 이어간다. 없다면 작업 지시, 현재 계획/기록, 실제 관련 코드만 읽는다. 허용 범위 밖 시스템이나 관련 없는 프로젝트를 탐색하지 않는다.
3. 마지막 승인 범위, 전체 설계와 현재 계획·변경 이유, 완료한 필수 기능, 실제 검증 결과, 남은 오류, 다음 작업을 짧게 재구성한다. 파일이 있다고 완료로 간주하지 않는다.
4. [인계에 남긴 운영 정보](work-record.md)와 실제 작업 경로·브랜치/파일 상태·staged/미커밋 변경을 대조한다. 기록과 코드가 다르면 변경된 근거를 확인하고 관련 검증만 다시 한다. 처음부터 재작성하거나 기존 파일을 초기화하지 않는다.
5. 서버·장기 실행 명령이 있었다면 기록된 프로세스/세션의 생존 여부, 실제 포트·경로·로그와 현재 응답을 확인한다. 예전 주소나 PID만으로 같은 서버가 살아 있다고 판단하지 않는다. 살아 있는 작업 서버는 재사용하고, 종료됐으면 원인과 현재 실행 조건을 확인해 승인된 명령으로 재시작한다. 인계 때문에 서버를 종료하거나 충돌한 임의 프로세스를 죽이지 않는다. 웹의 연결 문제는 [실행 점검](web-runtime.md)을 따른다.
6. 중단된 명령·부분 편집·병합은 종료 상태와 저장된 결과를 먼저 확인한다. 중복 저장·외부 작업을 일으킬 수 있는 명령은 완료 여부와 재실행 영향을 확인하기 전 반복하지 않는다. 불명확한 부분만 미확인으로 남긴다.
7. 현재 범위 안의 다음 작은 작업과 구체적인 명령/사용자 동작, 예상 결과를 정해 이어간다. 이전 승인을 알고 있다면 반복해서 승인받지 않는다. 새로 확인한 상태와 다음 행동만 기존 기록에 갱신한다.

## 시간 판단과 비용

사용자가 정한 마감·시간 예산이 있을 때 실제 확인한 현재 시각과 진행 상태를 기준으로 계획을 조정한다. 마감이 없으면 임의의 제한 시간을 만들지 않는다. 대기·승인·재접속도 일정에 영향을 줄 수 있다.

첫 실행 경로를 일찍 확인하고, 필수 요구 → 중요한 실패 위험 → 최종 검증/이해 확인 → 선택 개선 순으로 자원을 배분한다. 성능·모델·외부 의존성을 추가하면 정확성/운영/설명 비용도 평가한다.

시간이 부족하다고 확인되면:
- 현재 동작하는 필수 기능과 미검증·실패를 먼저 정리한다.
- 가장 큰 필수 위험 하나를 줄이는 작업부터 선택한다.
- 새 스택/대규모 재설계/선택 기능/장식 문서는 줄인다.
- 필수 요구를 임의로 삭제하지 않는다. 불가피한 미완료는 영향과 이유를 드러낸다.
- 최종 실행·저장·인계, 사용자의 확인에 필요한 시간을 계획에 포함한다.
- 동일 검사나 긴 보고를 반복하지 않는다. 스킬 설치/로드 자체가 막히면 우회·재설치를 반복하지 않고 허용된 기본 도구로 작업한다.

확인된 시간 때문에 우선순위를 바꾸면 바뀐 이유·다음 작업·남는 위험을 현재 계획에 반영한다.
