# 최소 작업 기록 — 구조화와 방향 변경을 이어가기

작업에서 지정한 계획서·보고서·협업 기록이 있으면 그 형식을 사용한다. 기존 문서의 현재 내용을 읽고 필요한 항목을 합친다. 기록 파일명 자체가 작업 품질을 보장하지 않는다. 최초 분석 중에는 아래 파일을 생성하지 않는다.

지정 형식이 없고 구현 범위가 결정됐다면 판단 이력은 DECISIONS.md, 검증 근거는 NOTES.md로 관리한다. 현재 구현의 설계 이유·교체 지점은 README 또는 허용된 설계 문서에 요약하고 결정·검사 기록과 연결한다. 큰 작업의 인계가 필요하면 HANDOFF.md를 사용한다. 매 명령마다 문서를 늘리지 않고 중요한 선택·검사·방향 전환에 갱신한다. 원본 TASK/README를 개인 계획으로 덮어쓰지 않는다.

## DECISIONS.md에 남길 현재 작업 계약

- 목적: 사용자/상황/문제, 기술적 완료 조건과 업무 효과의 구분.
- 필수 요구: R1… / 근거 / 완료 조건 / 구현 위치 / 검증 상태.
- 제약과 권한: 읽기 전용 / 수정 허용 / 유지 조건 / 재판단이 필요한 변경.
- 전체 설계: 핵심 입력→처리→출력 / 모듈·파일 책임 / 필요한 계약·상태·연결 경계 / 선택 근거와 미정인 부분.
- 현재 계획: 작업 A… / 관련 필수 요구 / 결과물 / 선행 조건 / AI 작업·사용자/담당자 확인 / 완료 검증 / 다음 판단 / 진행 상태.
- 계획 변경: 이전 순서·설계 → 새 계획 / 바꾼 근거 / 영향받는 요구·코드·검사·문서 / 유지할 제약 / 필요한 사용자 결정 또는 이미 승인된 범위.
- 중요한 결정: D1… / 관련 요구 R… / 결정 주체(작업·담당자·사용자·AI) / 선택·목적 / 근거와 조건 / 버린 대안과 이유 / 비용·위험 / 재검토 조건 / 구현 위치 / 검사 E… / 설계 문서 위치 / 현재 유효 여부.
- 사용자 이해: D…별 미확인·재설명 필요·설명 확인 / 실제 응답에서 확인한 내용·남은 오해 / 다음 확인. AI 선택의 이유·대안·성립 조건을 실제로 들은 경우만 설명 확인으로 기록한다.
- 담당자 대화: 담당자별 역할·답변 가능한 범위 / Q1… / 알고 싶은 점 / 앞선 질문·답과의 연결 / 실제 답과 출처 / 확인된 내용·남은 쟁점 / 다음 질문 / 답변 상태와 반영 상태. 작은 탐색 질문도 기록할 수 있으며 코드 변경을 필수로 요구하지 않는다.
- 다음 작업: 하나 또는 소수의 구체적 행동, 막힌 조건.

현재 계획은 위쪽 한 곳에 유지하고 변경 이유는 짧은 이력으로 남긴다. 모든 대화에 새 문서를 만들거나 변경이 없는데 기록을 다시 쓰지 않는다. 매 대화에서 유지/수정 여부를 확인하되 새 답·검사·가정·시간 변화가 실제 다음 행동을 바꿀 때 관련 기록을 갱신한다.

답변 상태(초안·답변 대기·일부 확인·확인·답변 불가)와 반영 상태(맥락 반영·구현 반영 필요·구현 반영/검증 전·검증 완료)를 구분한다. 업무 이해만 넓힌 답은 맥락에 반영한 것으로 충분하다. 일부만 답하면 확인한 내용을 버리지 않고 남은 쟁점만 후속 질문으로 연결한다. 질문을 다시 제안하기 전에 앞선 질문의 의도와 실제 답을 확인한다. 답변·정책·코드가 바뀌면 관련 결정과 검증을 점검하되 “답변 받음”을 “구현 완료”로 취급하지 않는다.

R(요구)→D(결정)→구현 위치→E(검사)→설계 문서 절→사용자 이해를 기존 기록 안에서 연결한다. ID는 간단한 참조용이며 새 데이터베이스·CLI나 모든 변경의 번호 매기기를 요구하지 않는다. 구현/검증/문서/이해 상태를 각각 관리한다. 예를 들어 코드와 검사가 완료돼도 README가 없으면 문서화 미완료이며, 사용자의 답이 없으면 이해는 미확인이다.

여러 대화에서 나온 요구는 현재 MVP 요약 한 곳으로 종합한다. 사용자·문제, 포함 범위, 핵심 흐름, 결과/피드백 형식, 제외 범위, 제약, 미확인 조건, 성공 기준과 출처 Q…를 담는다. 새 답에 따라 철회한 가정과 영향을 갱신하며 과거 기록은 정정 관계로 남긴다. [질문과 반영](stakeholder.md)의 확인 절차를 따른다.

## NOTES.md에 남길 검증 근거

| 검사 E… / 요구 R… / 결정 D… | 검사 입력·조건 | 예상과 근거 | 실행 명령/방법 | 실제 결과 | 판정/한계 | 확인 주체 | 검사한 코드·연결 방식·근거 위치 |
|---|---|---|---|---|---|---|---|

행은 실제 검사를 실행한 후 채운다. 계획만 세웠으면 미실행으로 표시한다. 긴 출력 대신 결과를 판단할 핵심 값과 로그 위치를 남긴다. 파일 변경 뒤 오래된 증거는 STALE로 표시하고 관련 검사를 갱신한다.

[검증한 상태의 식별 기준](evidence.md)에 따라 실제 커밋과 미커밋 변경 상태 또는 관련 파일 식별값, 입력·설정 버전, 모의/실제 연결과 검사 종류를 필요한 만큼 남긴다. 여러 검사가 같은 상태를 사용하면 공통 실행 기록 하나를 연결한다. 새 열이나 별도 파일을 강제하지 않고 기존 양식의 비고·로그 링크로 같은 정보를 전달해도 된다.

변경 시 관련 기록만 갱신한다. 코드/입력/설정/정책 변경은 영향받는 E를 STALE로 만들고 설계 문서의 일치 여부를 확인한다. AI 결정의 이유·대안·성립 조건까지 바뀌었으면 해당 D의 이해도 다시 확인한다. 문서 표현만 다듬은 경우 불필요하게 모든 검사를 재실행하지 않는다.

## HANDOFF.md가 필요한 경우

현재 목표·필수 요구, 승인된 변경 범위, 현재 계획과 최근 변경 근거, 중요한 결정, 구조와 핵심 파일, 실행/검사 명령과 실제 확인 결과, 미완료·위험, 다음 작업 하나를 남긴다. 새 세션은 기록뿐 아니라 실제 파일과 상태를 대조한다. 문서는 작업 중 맥락 유지와 인계·이해 확인에 사용한다.

재개에 필요한 운영 정보도 같은 기록에 짧게 남긴다. 해당 없는 항목은 생략한다.

- 실제 TASK 경로와 사용한 브랜치/커밋 또는 파일 상태, 남아 있는 staged·미커밋·새 파일과 미완료 편집.
- 마지막으로 확인한 동작과 그때의 코드·입력·설정, 검증 근거 위치. 기록 시각과 실제 확인 시각이 다르면 구분한다.
- 실행 중인 서버/명령의 역할, 실행 디렉터리와 정확한 명령, 실제 접속 주소·포트, 터미널/세션 또는 확인한 프로세스 식별자, 로그가 있으면 위치.
- 중단 시 실행 중·종료·실패·상태 미확인 중 어느 상태였는지, 진행 중인 병합이나 부분 처리 등 재실행 전 확인할 사항.
- 다음 작업 하나와 실행할 명령 또는 사용자 동작, 선행 확인과 예상 결과. 아직 실행하지 않은 다음 명령은 제안으로 표시한다.

비밀값이나 전체 대화를 복사하지 않는다. 다음 세션의 실제 확인과 서버 재사용·재시작은 [세션 복구](session-time.md)를 따른다.
