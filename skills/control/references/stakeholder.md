# 작은 질문에서 업무 이해와 구현으로 이어가기

작업 원문·자료·기존 답변부터 읽는다. 담당자의 첫 답에 필요한 정보가 모두 들어 있다고 가정하지 않는다. 작은 질문으로 맥락을 알아내고 실제 답에서 후속 질문을 발전시킨다. 질문 수를 최소화하거나 많이 채우는 것이 목표가 아니다. 업무를 더 정확히 이해하고 그 이해를 요구·설계·검증에 반영한다.

## 첫 질문은 답변 가능한 범위부터

처음 대화하는 담당자에게 보낼 첫 질문은 다음과 같이 제안한다.

> 어떤 정보를 답해 주실 수 있나요?

실제 답에서 알게 된 역할·업무·제공 가능한 정보·답변할 수 없는 범위를 짧게 정리한다. 답을 듣기 전에 그 범위를 지어내지 않는다. 이미 범위를 확인한 담당자와 대화를 재개할 때는 이 질문을 반복하지 않고 마지막 답에서 이어간다.

그다음은 용어, 현재 업무, 불편, 최근 사례 같은 작은 질문으로 시작해도 된다. 예: "왜 대시보드가 필요하다고 보셨나요?", "평소에는 어떤 화면을 먼저 보시나요?" 아직 어느 코드를 바꿀지 몰라도 업무 맥락을 알아보기 위한 질문은 유효하다. 한 번에 답하기 쉬운 한 주제를 묻고, 그 답을 보고 다음 질문을 고른다.

**"뭘 해야 하나요?", "만들 기능과 설계를 전부 정해 주세요"처럼 해결책·설계·판단을 통째로 요구하는 질문은 제안하지 않는다.** 업무 맥락을 묻는 "왜 필요하다고 보셨나요?"와 기술 작업을 대신 맡기는 요청을 구분한다.

## 답을 받으면 Codex가 다음 질문을 제안한다

사용자가 담당자 답을 전달할 때마다 Codex가 먼저 다음을 짧게 정리한다.

1. **새로 알게 된 점:** 실제 답에서 확인된 사실과 이전 이해의 차이.
2. **아직 모르는 점:** 답이 일부만 설명한 과정·판단·예외. 단서가 없으면 내용을 만들어 채우지 않는다.
3. **다음 질문:** 방금 답의 구체적인 표현을 받아 사용자가 보낼 문장과 묻는 이유를 제안한다. 구현 영향은 알게 된 범위에서 설명하며 탐색 단계에서는 "업무 흐름 파악"만으로도 충분하다.
4. **현재 계획:** 바로 반영할 맥락·요구·설계·검증과, 추가 확인을 기다릴 부분을 구분한다.

다음은 답에서 발전시킬 수 있는 흐름의 예시다. 고정 질문 목록을 한꺼번에 보내거나 답을 미리 작성하지 않는다.

- 필요성·불편을 들었다면 → "말씀하신 불편이 생긴 최근 사례를 하나 설명해 주실 수 있나요?"
- 실제 사례를 들었다면 → "그때 누가 어떤 정보를 보고 판단했나요?"
- 판단 과정을 들었다면 → "그 판단에서 가장 어려웠던 부분은 무엇인가요?"
- 어려움이 구체화됐다면 → "그 상황에서 어떤 정보가 먼저 보이면 다음 행동을 정하기 쉬울까요?"
- 원하는 행동을 알게 됐다면 → "그 사례에서 개선됐다고 판단할 수 있는 변화는 무엇인가요?"

관점은 최근 사례→행동 주체·순서→판단 근거→병목·예외→성공 기준으로 깊어질 수 있다. 답에 따라 순서를 바꾸고 이미 확인된 항목은 건너뛴다. "최근 사례는요?"도 맥락에 맞는 유효한 후속 질문이다. 중요한 주제가 충분히 확인됐다면 무엇이 확인됐는지 밝히고 요약 확인이나 다음 주제를 제안한다. 억지로 질문을 만들어 계속 묻지는 않는다.

## 중복 질문과 제한적인 답변 다루기

제안 전에 이전 질문의 **표현이 아니라 의도와 실제 답**을 확인한다. 이미 답한 성공 기준을 같은 문장이나 동의어로 다시 묻지 않는다. 추가 확인이 필요하면 이전 답을 짚고 남은 부분만 묻는다. 예: 성공 기준으로 "판단 시간을 줄이고 싶다"고 답했다면 "말씀하신 판단 시간은 어느 행동에서 시작해 어느 행동에서 끝나나요?"처럼 구체화한다. 아직 듣지 못한 답을 전제로 쓰지 않는다.

답이 짧거나 모호하면 최근 한 사례·용어 하나·판단 단계 하나로 좁혀 후속 질문을 제안한다. 일부만 답했으면 확인된 내용은 보존하고 남은 쟁점만 묻는다. 답변 불가라고 하면 처음 확인한 역할·정보 범위 안에서 답할 수 있는 인접 주제를 제안하거나 적절한 담당자·해당 환경의 지원 경로를 구분한다. 같은 거절을 반복 유도하거나 제한된 정보를 우회해 요구하지 않는다.

사용자가 직접 전송하고 실제 답변만 반영한다. Skill은 질문을 자동 전송하거나 담당자/사용자의 답을 만들어내지 않는다. 질문 초안을 만들었다는 사실을 실제 질문·답변·합의로 기록하지 않는다.

## 직접 검증과 담당자 탐색을 함께 진행한다

자료 검토·집계·검증에서 확인할 것이 생겨도 사용자가 먼저 묻기를 기다리지 않는다. 초기 설계와 계획에 대화·검증 시점을 넣고 새 답과 결과에 따라 갱신한다. 자료의 계산과 코드 설명은 Codex가 맡고, 실제 업무 맥락은 담당자에게 확인한다. 자료에 쓰인 용어의 현장 의미나 이해가 맞는지 확인하는 작은 질문도 허용한다.

| 확인할 내용 | 확인 주체와 방법 | 다음 결정 |
|---|---|---|
| 수치·동작이 자료/규칙과 일치하는가 | Codex가 원자료 검산·코드/함수/HTTP 검사 | 구현 수정 또는 업무 기준 질문 |
| 실제 화면에서 핵심 행동이 가능한가 | 사용자가 제시된 동작과 예상 결과를 직접 확인 | UI 완료/미확인, 수정 범위 |
| 역할·용어·최근 사례·판단 과정은 무엇인가 | 사용자가 작은 탐색 질문을 전송하고 답에서 후속 질문 | 업무 이해 갱신·새 쟁점 발견 |
| 포함·제외 기준, 우선순위, 실제 예외는 무엇인가 | 사용자가 담당자에게 구체적인 업무 질문 전송 | 요구·정책·성공 기준 확정/보류 |
| 환경 사용법 또는 플랫폼 장애인가 | 해당 환경의 문서·관리자·지원 채널 확인 | 실행 절차·허용된 복구 |

추천에는 **자료 또는 이전 답의 단서 → 알고 싶은 점 → 확인 방법/보낼 질문 → 새로 알면 반영할 곳**을 붙인다. 탐색 질문에 당장의 코드 변경이나 진행 차단 사유를 억지로 요구하지 않는다. 필요한 업무 기준이 없어서 실제 작업이 막히는 경우에만 보류할 부분을 표시한다.

예를 들어 보고서 평균이 의심되면 기간·단위·건수·분모·제외 규칙을 자료에서 찾아 직접 재계산한다. 불일치가 남고 업무 기준이 자료에 없을 때 "보고서의 평균은 완료 건만 대상으로 하나요, 진행 중인 건도 포함하나요? 포함 대상을 확정해 집계 로직과 기대값을 정하려 합니다."처럼 실제로 필요한 쟁점 하나로 좁혀 묻는다. 아직 검산하지 않았다면 "불일치"가 아니라 "검증 전"으로 표시한다. 담당자에게 Codex의 계산을 대신 시키거나 코드 설계를 떠넘기지 않는다.

## 응답 이후가 의도 관리다

질문의 답변 상태와 구현 반영 상태를 분리한다.

- **답변 상태:** 초안 / 답변 대기 / 일부 확인 / 확인 / 답변 불가. 실제로 받은 정보와 남은 쟁점을 함께 남긴다.
- **반영 상태:** 맥락 반영 / 구현 반영 필요 / 구현 반영·검증 전 / 검증 완료. 코드 변경이 필요 없는 탐색 답변은 맥락에 반영한 것으로 충분하며 테스트를 억지로 만들지 않는다.

실제 답과 출처, 이전 가정과 차이, 영향받는 요구·설계·작업 순서·코드·검사·문서를 연결한다. “답을 받았다”를 “기능을 반영했다”로 보고하지 않는다. 답이 기존 결정을 바꾸면 원인과 수정 범위를 먼저 설명하고 현재 계획과 관련 검증을 갱신한다. 업무상 답변과 사용자의 구현 범위 승인은 구분한다.

답변이 상충하면 권위·적용 시점·대상 범위를 확인한다. 날짜가 최신이거나 자주 인용됐다는 이유만으로 업무 정책을 확정하지 않는다.

답이 없으면 임시 가정과 영향을 명시하고 사용자에게 추천안을 제시한다. 잘못된 확정이 큰 영향을 주면 보류·명시적 오류 등을 제안한다. 미확인 조건과 무관한 승인 작업은 계속한다. 사용자의 가정을 담당자 승인이나 자료의 사실로 바꾸지 않는다.

## 여러 대화를 현재의 MVP 정의로 종합한다

초기 범위를 정할 때와 범위·흐름·정책을 바꾸는 답변이 들어왔을 때, 여러 담당자·대화·자료의 내용을 하나의 현재 요약으로 합친다. 메시지별로 문서를 늘리거나 과거 요약을 나열하는 것으로 대신하지 않는다.

요약에는 **사용자와 문제 / 포함 범위 / 핵심 사용 흐름 / 결과·피드백 형식 / 제외 범위 / 유지할 제약 / 미확인 조건 / 성공 기준**을 담는다. 항목마다 실제 답변 Q…·자료 위치를 연결하고 담당자가 확인한 사실, 사용자의 선택, AI의 제안·가정을 구분한다. 핵심 요구가 누락된 것을 MVP라는 이름으로 정당화하지 않는다.

새 정보가 들어오면 유지하는 내용, 철회하는 가정, 수정할 흐름·코드·검사를 함께 표시하고 현재 요약을 갱신한다. 상충한 답변을 조용히 한쪽으로 합치지 않고 권위·적용 시점·대상을 확인한다.

업무상 확인이 필요한 내용은 사용자가 담당자에게 되돌려 보낼 짧은 확인 문구로 정리한다.

> 지금까지 말씀을 종합하면 대상은 …, 필수 흐름은 …, 결과 형식은 …입니다. …는 제외하되 … 제약은 유지하겠습니다. 새 답변에 따라 기존 … 가정을 철회하고 …를 바꾸려 합니다. 아직 확인되지 않은 …에 이 기준을 적용해도 될까요?

확인 문구는 초안이며 사용자가 직접 전송한다. 실제 전송·답변이 없으면 “확인 요청 초안/미확인”으로 남기고 담당자 합의나 승인으로 기록하지 않는다. 단순한 내부 기술 변경마다 담당자에게 전체 요약을 반복 전송하도록 요구하지 않는다.
