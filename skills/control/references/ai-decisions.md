# AI가 내린 결정과 근거를 사용자가 이해하기

사용자가 정한 목표를 이해하는 것과 AI가 그 목표를 구현하기 위해 고른 방법을 이해하는 것은 별개다. 개발 단계의 중요한 선택 직후 이 지침을 적용한다. 최초 분석에서는 제안과 근거만 설명하고, 기록 생성은 구현 범위 결정 이후에 한다.

## 어떤 결정을 다룰 것인가

라이브러리, 자료구조, 데이터 계약, 저장/캐시, 알고리즘, 임계값, 실패·예외 처리 중 결과·유지보수·비용·위험에 영향을 주는 것을 고른다. 같은 근거로 묶이는 선택은 함께 설명하고 변수명 같은 사소한 선택마다 멈추지 않는다. 사용자에게 익숙하지 않은 선택과 틀렸을 때 영향이 큰 선택부터 다룬다.

결정 주체를 구분한다: **작업 지정 / 담당자 결정 / 사용자 결정 / AI 제안**. 여러 주체가 관여하면 AI 제안과 실제 채택한 사람·근거를 나눠 적는다. 라이브러리 선택 같은 기술 판단은 승인 범위에서 AI가 할 수 있다. 업무상 적합/부적합을 가르는 임계값·제외 정책은 기술적 기본값처럼 임의 확정하지 않는다.

## 짧은 결정 설명

중요 결정 D1…을 기존 기록에 연결한다.

- **선택과 목적:** 무엇을 선택해 어떤 요구를 해결하는가.
- **근거와 조건:** 실제 작업 제약·자료·검사·측정 중 무엇을 확인했는가. 관찰과 추론을 구분한다.
- **대안과 포기 이유:** 현실적인 대안 하나 이상과 현재 선택하지 않은 이유. 실행 비교를 안 했다면 성능을 측정한 것처럼 쓰지 않는다.
- **비용·위험:** 구현 시간, 복잡도, 의존성, 자원·운영 비용, 실패 조건 중 관련된 것.
- **재검토 조건:** 데이터 크기·정확도·업무 정책·실행 환경 등이 어떻게 바뀌면 대안이 나아지는가.
- **구현·증거:** 실제 파일/함수·설정, 관련 검사 E1…, README/설계 문서의 해당 절.

임의로 둔 값은 임시 가정으로 남긴다. 기존 코드의 선택 이유를 알 수 없다면 원래 의도는 미확인이라고 말하고 현재 코드의 효과·위험을 설명한다. 선택 후 그럴듯한 근거나 실행하지 않은 비교 결과를 만들어 붙이지 않는다.

## 재설명과 이해 상태

선택을 설명한 뒤 사용자에게 중요한 한 가지를 묻는다. 세 질문을 매번 모두 요구하지 않는다.

1. **이유·대안:** 이 방법을 고른 이유와 버린 대안은 무엇인가?
2. **성립 조건·위험:** 어떤 입력이나 환경에서는 이 선택이 문제가 되는가?
3. **변경 적용:** 조건이 바뀌면 무엇을 다시 선택하고 어떤 코드·검사를 바꿔야 하는가?

사용자가 자기 말로 이유·대안·조건을 설명했는지 실제 답변을 보고 판정한다. 핵심 선택에 대한 여러 차례의 답을 합칠 수 있다. 정확한 용어 암기보다 인과관계 이해를 본다. AI 설명을 복사하거나 "알겠어"라고만 한 응답은 이해 확인으로 충분하지 않다.

- **미확인:** 아직 답을 듣지 못했거나 확인할 근거가 부족함.
- **재설명 필요:** 선택 이유·대안·위험에 중요한 오해가 있음. 구체적인 차이를 코드/자료로 교정한 뒤 다시 말해 보게 함.
- **설명 확인:** 실제 답변에서 핵심 이유·대안·성립 조건을 확인함. 필요한 경우 설명 후 확인했다는 사실도 남김.

사용자가 지금 답하기 어렵다면 미확인으로 남기고 승인된 독립 작업은 이어간다. 구현 완료나 결과물 전달을 이해 상태로 강제 차단하지 않는다. 중요한 미확인 결정은 인계 시 확인할 항목으로 드러낸다. 사용자가 설명이나 작업을 중단하라고 하면 따른다.

## 변경된 결정은 다시 확인한다

정책·구조·실패 처리 또는 선택 이유를 바꿀 새로운 증거가 생기면 기존 D 기록을 정정 내역과 연결하고 관련 문서·검사를 갱신한다. 이유·성립 조건이 달라졌다면 해당 이해 상태도 미확인으로 돌린다. 이유가 그대로인 오탈자·스타일 수정 때문에 전체 이해 확인을 반복하지 않는다.
